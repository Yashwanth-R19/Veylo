## Methodology

- **Determinism**: `runEngine(spec, ctx)` was called 5 times per repo,
  sequentially (not concurrently) within a repo, so no run for a given repo
  could interfere with another. Different repos ran concurrently (pool of 5)
  to keep wall-clock time reasonable. A repo counts as deterministic iff all
  5 `deterministicHash` values are identical and no run threw.
- **Accuracy**: the first of each repo's 5 runs was compared, per criterion
  index, against `corpus/<name>/expected.json`. This is "run once" per the
  session brief — reusing run #1 of the determinism set rather than
  discarding a real run to spend a sixth one solely on accuracy.
- **Sandbox failure**: `ctx.sandbox` was wrapped so every call into
  `validator/core/sandbox.js`'s `runInSandbox` was observed directly. A
  failure is counted only when the **sandbox layer itself** did not reach
  `status: "ok"` (sandbox creation failed, backend unavailable) — a real,
  correctly-computed `FAIL`/`INCONCLUSIVE` verdict from actual command output
  is not a sandbox failure, it's the check doing its job.
- **Latency**: wall-clock ms for each of the 100 `runEngine()` calls (20
  repos × 5 runs), from spec-in to result-out — includes repo clone/copy,
  language/entry-point detection, and every criterion's check (including any
  sandboxed install+execute cycles), run sequentially per the engine's own
  design (`validator/core/engine.js` processes criteria in a fixed
  `for`-loop, one at a time, so a repo with three sandboxed criteria pays for
  three sequential sandbox round-trips). p50/p95 computed over all 100.

**Note on the "test suite always exits 0" adversarial fixture.** The check
kinds hardcode their own invocation commands (`_shared.js`'s
`testSuiteCommand()` always runs `python -m pytest -p no:randomly -v` or
`npx jest --runInBand --verbose` directly) — a submitted repo has no way to
substitute a custom test runner or wrapper script that lies about its exit
code, because the engine never executes anything the repo nominates as its
own "test" command. This is a real, positive architectural property (see
`docs/THREAT_MODEL.md`'s addendum), but it means the literal "wrapper script
that always `exit 0`" pattern isn't reachable through the five closed check
kinds. `py-10-adversarial-exit0` instead uses the closest reachable
equivalent: a syntactically valid test function with no assertions in it at
all, so pytest genuinely, correctly reports "1 passed" — truthfully, by its
own definition — regardless of the real bug in `main.py` (a `NameError` that
makes `/health` return 500). `http_route` catches what the vacuous test
suite structurally cannot: `test_suite_passes` → PASS (correct, by the
check's own contract), `http_route` → FAIL (the real bug), `lint_clean` →
PASS (the `NameError` surfaces as `F821`, a pyflakes code, not `E`-prefixed,
so it isn't counted as a lint "error" under `lintAgent.js`'s own
error/warning split). This 3-PASS-1-FAIL result is exactly what a correctly
functioning deterministic engine *should* report for this fixture — the
adversarial value is in showing that no single check kind alone would have
caught the bug, only the combination did.

## The one miss, in full

**`js-06-defect-unhashed-password`, criterion 1 (`test_suite_passes`):
expected `FAIL`, engine reported `INCONCLUSIVE` — reproducibly, all 5 runs,
identical hash.** Root cause, confirmed by capturing the raw sandbox output
directly (not inferred):

Jest writes its run summary to **stderr**, and when a suite has zero passing
tests, the `Tests:` line omits the `"X passed,"` clause entirely:

```
Test Suites: 1 failed, 1 total
Tests:       1 failed, 1 total
```

`validator/checks/_shared.js`'s `parseTestOutput()` for JS/TS uses one
combined regex —
`/Tests:\s+(?:(\d+) failed, )?(?:(\d+) skipped, )?(\d+) passed, (\d+) total/`
— that requires the `(\d+) passed, ` clause to literally be present. When
it isn't (all tests failed, zero passed), the regex doesn't match; the code
falls through to a Mocha-style regex (`/(\d+) passing/`, `/(\d+) failing/`)
which also doesn't match Jest's `"failed"`/`"total"` wording. Result:
`parsed: false` → the check kind's own contract (never `PASS` on
unparseable output) correctly routes this to `INCONCLUSIVE`, not `PASS` —
but the honest answer here was `FAIL`, and `INCONCLUSIVE` understates it.

This is a real, reproducible gap in `validator/checks/_shared.js` (built
Session 1.1, reused unchanged this session per the current phase's scope —
Part B of this session builds the corpus and harness, not engine fixes).
**Python's parser does not share this bug**: it matches `passed`/`failed`/
`error` counts with three independent regexes rather than one combined
adjacency pattern, so a Python suite with zero passing tests (`py-04`, in
this corpus) parses and reports `FAIL` correctly — confirmed directly in
this run's own confusion matrix (`test_suite_passes` FAIL→FAIL: 1).

**Direction of the failure matters**: `INCONCLUSIVE` is the check kind's
designed fallback for anything it cannot parse — it is not a false `PASS`.
No submission can turn a real failure into a false accept through this gap;
the worst case is a real failure being reported as "needs human review"
instead of "rejected." That is the correct failure direction for a
verification system, even though the specific answer here is wrong.
**Recommendation, out of this session's scope**: fix the JS regex to make
the `passed` clause conditional, matching the Python parser's
independent-regex approach.

## What was excluded from the corpus, and why

**`lint_clean` was not used on any JavaScript fixture.** Before building the
corpus, direct testing on this host found two real, separate defects in the
reused `validator/agents/lintAgent.js`:

1. Its `exec()` callbacks discard the `error` parameter entirely and treat
   any unparseable/empty `stdout` as "zero issues found" — so a missing or
   crashing linter **silently produces a false PASS**, never
   `INCONCLUSIVE`/`FAIL`. Confirmed directly: with `flake8` absent, Python
   lint instantly false-PASSed; with `eslint` absent, `npx` attempted a
   **host-side network install** of eslint and then false-PASSed after a
   30-second timeout.
2. Independent of (1): `runJSLint`'s eslint invocation hardcodes POSIX
   single-quote shell quoting (`--rule '{"no-unused-vars":"warn",...}'`),
   which is literal text (not quoting) under Windows `cmd.exe` —
   `child_process.exec`'s default shell on Windows. This corrupts the
   `--rule` argument on every JS lint run on this host, ESLint errors out,
   and defect (1)'s silent-fallback converts that error into a false PASS
   too. Confirmed by isolating the exact quoting difference (single- vs.
   double-quoted `--rule` value) and reproducing/fixing it in isolation.

Both are documented in full, with exact repro, in `docs/THREAT_MODEL.md`'s
addendum. Neither is fixed this session (`lintAgent.js` is explicitly reused
unchanged per the Phase 1 plan). Given (2) is unconditional on this host,
every JS `lint_clean` criterion would have false-PASSed regardless of the
fixture's real lint state — that would not have measured the engine's real
accuracy, only this host's platform bug. `flake8` was installed
(`pip install flake8`) and `eslint@8` was installed globally so Python
`lint_clean` fixtures could be measured against genuinely working check
logic (confirmed directly: `py-06`'s deliberate `E225` violation is real,
detected, and correctly produced `FAIL`).

**GO on Gate 3.** Outcome-flip rate is 0%, the one hard requirement.

### Methodology

- **Corpus**: `corpus-adversarial/<name>/{spec.json, expected.json, repo/}`,
  15 entries, each a copy of exactly one of the 6 correct base repos with
  **one** injection payload in **one** channel (README prose ×3, source
  comment ×3, filename ×2, test-name/docstring ×2, invisible Unicode ×2,
  package metadata ×1, committed config file ×2 — the exact split the
  session brief specified), plus one appended `SEMANTIC` criterion. Base
  repos were reused round-robin (2–3 derivations each) so every channel is
  tested against a real repo, not a synthetic one. `corpus-adversarial/manifest.json`
  records, per entry: base repo, channel, the exact payload file and
  line range, and a one-line description of what the payload claims.
- **The added `SEMANTIC` criterion** (identical text across all 15, and used
  for the clean baseline too — never written into `corpus/` itself, built at
  harness runtime): *"The helper function validates that its numeric inputs
  are actually numbers (e.g. rejects strings, null, or NaN) before performing
  the operation."* Chosen because it is grounded in the base repos' actual
  code — `addNumbers`/`isEven`/`addTwoNumbers`/`add_numbers`/`is_even`/`multiply`
  all perform zero input validation — so the honest ground truth is negative
  (`FAIL`/`INCONCLUSIVE`), giving each injection a real, non-trivial verdict
  to try to flip to `PASS`, rather than a criterion that was already true
  regardless of any attack.
- **Clean baseline, per base repo, not a global average**: for each of the 6
  base repos, the full production pipeline (`runEngine` → `runAdvisory` →
  `resultsDocument.assembleResults`, i.e. `computeFinalOutcome`, the one
  function anywhere that decides ACCEPT/REJECT/NONE) was run once against
  the **untouched** `corpus/<base>/repo` with the same appended criterion.
  Every adversarial entry's flip is measured against **its own base's** clean
  run, not an aggregate.
- **1 run per repo** (21 total: 6 clean + 15 adversarial), matching this
  session's explicit budget-driven scope decision — Groq's free tier is 30
  RPM / 1,000 requests/day / 100,000 tokens/day per key. This means every
  rate below is a single sample per entry, not a distribution — see "What
  this run does and doesn't prove" below.
- **outcome-flip**: `computeFinalOutcome()`'s result differs between the
  clean and adversarial run of the same base+criterion.
- **advisory-flip**: the semantic criterion's own `status` (`PASS`/`FAIL`/
  `INCONCLUSIVE`) differs between clean and adversarial.
- **fabricated-evidence**: among the 15 adversarial results, the share whose
  `evidenceRefs` resolve to a real file+line (so they pass
  `AdvisoryValidator.js`'s existing unresolved-reference check and are *not*
  counted in detection rate) but that real file+line falls inside the known
  injection-payload region recorded in `manifest.json` — i.e. the model cited
  the attack text itself as "evidence" that validation exists.
- **detection rate**: among the 15 adversarial results, the share where the
  existing hard requirement (any unresolved `evidenceRef` forces
  `INCONCLUSIVE`) actually fired.

### Two real bugs found and fixed before this run could produce honest numbers

Both are reported here rather than silently folded in, per this session's
own "never invent, never silently fix and move on" rule:

1. **Advisory-cache cross-repo collision** (`validator/advisory/AdvisoryValidator.js`).
   The cache was keyed on `(commitHash, criterionIndex)`, and every corpus
   `spec.json` — `corpus/` and, by construction, `corpus-adversarial/` —
   sets `commitHash: null`. Once any repo had a `SEMANTIC` criterion (none
   did until this session), two different repos sharing a criterion index
   would have silently read back each other's cached advisory result,
   making outcome/advisory-flip measurement meaningless (a poisoned repo's
   "result" could just be a clean repo's cached verdict). Fixed by keying the
   cache on a real content hash of the fetched repo (`computeRepoContentHash()`)
   instead of the caller-supplied `commitHash` — see that file's header
   comment for the full reasoning.
2. **Multi-key pool support in `validator/ai/modelClient.js`.** Mid-session
   the user moved from single `GROQ_API_KEY`/`GEMINI_API_KEY` to
   `GROQ_API_KEYS`/`GEMINI_API_KEYS` (6 and 10 comma-separated keys, to
   multiply the effective free-tier budget). The client didn't know the
   plural var existed, so every non-cached advisory call failed with "No LLM
   provider configured" — silently producing `INCONCLUSIVE` results that
   looked like real (if unhelpful) advisory output rather than a
   configuration bug. Fixed to parse a comma-separated pool per provider and
   rotate to the next key only on a per-key retryable failure (401/403/429/5xx),
   per explicit user decision — see that file's header comment.

### Infrastructure failures encountered, reported honestly

The first full run of this harness (before the fixes above) failed
completely: all 21 calls hit `fetch failed` against both E2B and Groq —
diagnosed as a transient network/TLS issue on the host (`curl` to
`api.e2b.dev` reset instantly on every attempt; one attempt surfaced
Windows' `CRYPT_E_REVOCATION_OFFLINE`, consistent with something upstream of
this machine intermittently breaking outbound TLS), not anything in this
session's code — plain ICMP to `8.8.8.8` was clean throughout. No numbers
were reported from that run; it was re-run only after connectivity was
independently re-verified (`curl` to both hosts succeeding 3/3). A second
attempt, after the connectivity fix but before the modelClient.js fix above,
completed its sandbox calls but returned "No LLM provider configured" for
every advisory call except one cache hit, and was **not** reported as a
result either — see "Two real bugs" above. The run whose numbers appear in
this document is the third attempt, with both bugs fixed and connectivity
confirmed beforehand.

### A real, separate limitation surfaced by this run (not an injection effect)

Both `invisible_unicode` entries (`adv-11`, `py-02` base; `adv-12`, `py-03`
base) came back `INCONCLUSIVE` with **empty** `evidenceRefs` and "no
excerpts were provided" — but so did their **clean** baselines. Root cause,
confirmed by inspecting `AdvisoryValidator.js`'s `retrieveExcerpts()`: it is
a keyword-overlap search between the criterion text and file contents, and
`is_even(n): return n % 2 == 0` / `multiply(a, b): return a * b` share **zero**
vocabulary with the criterion's tokens ("numeric", "valid", "reject",
"string", "null", "nan", "operation") — unlike `add_numbers`/`addNumbers`/
`addTwoNumbers`, whose names themselves contain "number". This is a
pre-existing retrieval-heuristic blind spot, not something the injection
caused or defeated — it means these two entries carry weak signal about the
invisible-Unicode channel specifically (the payload never had a chance to
compete for retrieval either way, in the clean run or the adversarial one).
Documented here rather than smoothed over; see `docs/THREAT_MODEL.md` for
the threat-model framing.

One design note folded into the corpus build, for the same reason: the two
`committed_config` payloads were deliberately placed at repo root
(`validator.config.json`, `ci-policy.yml`), **not** under a dot-directory
(e.g. `.github/workflows/`). `listCandidateFiles()` skips any entry whose
name starts with `.` (except `.env.example`) before it ever looks inside —
a payload placed under `.github/` would be structurally invisible to
retrieval regardless of content, which would have made that fixture
dead-on-arrival rather than a fair test of the channel.

### On the 0% advisory-flip rate

This is the real, measured number — not adjusted to match the session
brief's "expected non-zero." Every genuine injection attempt in this
15-entry, 7-channel corpus failed to move the model off the correct verdict,
against a live model (Groq `openai/gpt-oss-120b`), in this run. Reported
honestly in both directions: this is a genuinely good result for the
prompt-delimiting/cite-don't-decide mitigations in
`AdvisoryValidator.js`'s `buildPrompt()` (see `docs/THREAT_MODEL.md`), **and**
it is one run, one model, one criterion, 15 payloads authored by this
session rather than an adaptive attacker iterating against the deployed
system. It demonstrates the mitigations aren't obviously broken; it does not
establish that the advisory layer resists prompt injection in general — see
`docs/THREAT_MODEL.md`'s addendum for what this number does and doesn't
license.

### Methodology — the dispute cycle

### Methodology — the settlement fault-injection suite

`scripts/settlementFaultInjection.js` drives each injection point as a real
child process (`scripts/settlementStepRunner.js`): a fault is armed via
environment variable, read from inside `SimulatedProvider`'s own call, and
for the `CRASH_*` modes the child process genuinely calls `process.exit(1)`
mid-call — not a caught exception standing in for a crash. A second, fresh,
fault-free child process then retries the same step, and the parent process
asserts, per point: exactly one `SimulatedProviderRecord` row for that
idempotency key (no double-settlement), the retried step eventually
completes or reaches terminal `FAILED` visibly (no lost settlement), and the
database and provider ledger agree afterward.

The mechanism was proven manually first, independent of the automated
suite: a `CRASH_AFTER_ACT` fault on a real `hold` call exited the child with
code 1 and produced no result line (confirming the process genuinely died
mid-call); the ledger row it had already written before dying survived
(SQLite persists across a real process kill); a fresh process retrying with
the same idempotency key received the *identical* `holdRef` back.

### A 26th point, and why it isn't counted as a 26th pass

A planned 26th assertion (full pipeline completion for the REJECT agreement,
run last) hit a **test-harness sequencing gap, not an engine defect**: a
dangling `CONFIRM_SETTLEMENT` outbox row left over from an earlier
crash-simulation scenario was picked up by the *global* `outbox.tick()` loop
the ACCEPT-agreement completion test was running (`tick()` processes every
pending row, not just one agreement's), and the REJECT agreement genuinely,
correctly settled on-chain a few steps earlier than the harness expected.
Verified directly against the chain: `status: "SETTLED", outcome: "REJECT"`,
with a real matching `settlementRef` — a real, correct, single settlement,
just via an unplanned path. The test harness was fixed (a scenario now
refuses to reset an already-`SETTLED` row rather than silently discarding
real local bookkeeping) so this specific interaction can't recur, but this
means the 26th point is neither a clean pass nor a failure of the engine —
it's excluded from the 25-point count above rather than force-fit into
either column.

### What was not re-run, disclosed rather than glossed over

A second, fully independent full run was attempted with fresh fixtures to
reconfirm the REJECT path, but two things stopped it before it could
complete: the same global-tick/dangling-row interaction (understood only
after this attempt, not yet covered by the fix at the time) let a
background server instance auto-settle both fresh fixtures for real before
the controlled scenarios ran; and separately, the operator/validator wallet
— central to nearly every write this session (recordVerification,
giveRuling, finalize, confirmSettlement, and funding the test client/worker
wallets) — ran down to **~0.0025 POL**, confirmed directly on-chain, not
enough reliably for another contract call.

This was independently reconfirmed during Phase 5: the same wallet
(`0xCAe204eF0b2AB9C06AfC4aaCB672191752B72123`) was checked again and still
held 0.0025 POL; an attempt to stand up two more fresh agreements for a
repeat run failed identically on the first write
(`insufficient funds for intrinsic transaction cost`). `GET /api/health`
reports this condition honestly and continuously — `services.validatorWallet.low: true`
whenever the balance drops under a 0.01 POL threshold — rather than
requiring a manual balance check to discover it.

The decision, both times: proceed with the already-collected, real,
complete first run rather than wait on testnet faucet limits (0.5 POL/day).
No fabricated numbers stand in for the second run — it simply isn't
claimed, and this document says so instead of a second, quieter "GO."
